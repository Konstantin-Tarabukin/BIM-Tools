# RevitCopyParams — Roadmap

## Sprint 1 — Основа журнала изменений ✅

Цель: создать минимально рабочий журнал изменений.

Реализовано:

* создание `ChangeRecord`;
* окно журнала изменений;
* окно создания записи;
* сохранение журнала в Extensible Storage;
* загрузка журнала;
* сохранение автора;
* сохранение даты;
* сохранение модели-источника;
* выбор моделей-получателей.

Статус: завершён.

---

## Sprint 2 — Уведомления между моделями ✅

Цель: передавать записи журнала пользователям связанных моделей.

Реализовано:

* чтение журналов загруженных связанных моделей;
* фильтрация записей по `TargetModels`;
* окно уведомлений;
* проверка уведомлений при открытии документа;
* проверка уведомлений после синхронизации;
* проверка уведомлений после Reload Latest.

Основная механика уведомлений реализована.

Выявлен технический дефект:

* после Sync связанный `RevitLinkDocument` может оставаться
  в старом состоянии;
* `NotificationService` в этом случае корректно выполняется,
  но читает предыдущую версию журнала.

Первоначально проблема должна была решаться автоматическим Reload
связанных моделей.

После принятия ADR-014 внешний журнал становится предпочтительным
механизмом доставки уведомлений.

Текущий Extensible Storage-механизм сохраняется как fallback
до завершения JSON POC.

Статус: основная механика завершена; переход на внешний журнал
запланирован.

## Sprint 3 — Состояние прочтения ✅

Цель: сохранять персональное состояние прочтения уведомлений.

Реализовано:

* `NotificationStateService`;
* отдельное хранилище Extensible Storage;
* хранение прочитанных `Guid`;
* методы `IsRead` и `MarkAsRead`;
* массовая отметка уведомлений как прочитанных;
* статусы `Mine`, `New`, `Read`;
* WPF-конвертеры текста и цвета статуса;
* корректное определение статуса записи;
* сортировка журнала по статусу и дате.

Для внешнего JSON-журнала будет использоваться отдельное
локальное состояние клиента:

```text
%AppData%\BIMTools\RevitCopyParams\JournalState.json
```

Статус: завершён для текущей архитектуры;
внешний механизм состояния входит в JSON POC.

## Sprint 4 — UX журнала 🟡

Цель: сделать журнал удобным для повседневной работы.

Реализовано:

* открытие карточки клавишей Enter;

Осталось:

* [ ] пустое состояние журнала: «Изменений нет»;
* [ ] фильтр «Все»;

* [ ] фильтр «Мои».

Дополнительно:

  которых больше нет ни в одной записи.

При внедрении внешнего журнала UX уведомлений не должен требовать
автоматического Reload связанных моделей.

Статус: в разработке.

# Техническое направление A — Внешний JSON Journal 🟡

## Цель

Перенести доставку информации об изменениях из механизма:

```text
Extensible Storage
→ Revit Links
→ Reload
→ Notification
```

в механизм:

```text
Change
→ JSON Journal
→ Reader
→ Notification
```

без изменения существующего production-механизма
до завершения POC.

Цель эксперимента:

```text
Sync
→ запись внешнего события
→ другой Revit видит изменение
→ notification
```

без Reload исходной модели.

---

## Архитектурное решение

Для POC используется уже существующая сетевая структура проектов:

```text
R:\05091-ЭФ25\
├── AR\
├── KR\
├── VK\
├── OV\
└── _BIMToolsJournal\
```

Структура журнала:

```text
_BIMToolsJournal\
└── Events\
    └── YYYY\
        └── MM\
            └── DD\
                └── Model\
```

Пример:

```text
05091-ЭФ25\
└── _BIMToolsJournal\
    └── Events\
        └── 2026\
            └── 09\
                └── 08\
                    ├── AR\
                    ├── KR\
                    ├── VK\
                    └── OV\
```

Журнал каждого проекта физически находится
в его существующем каталоге.

# Техническое направление B — RevitLinkReloadService 🟡

## Цель

Сохранить корректную работу текущей
Extensible Storage-архитектуры на переходном этапе.

### Текущий статус

Автоматический Reload после Sync больше не является
целевым механизмом для нового внешнего журнала.

### План

* [ ] не блокировать JSON POC разработкой сложной оптимизации;
* [ ] сохранить возможность использования Reload
  для legacy Extensible Storage;
* [ ] при необходимости реализовать минимальный безопасный
  `RevitLinkReloadService`;
* [ ] проверять `IsNotLoadedIntoMultipleOpenDocuments()`;
* [ ] не ломать Sync при невозможности Reload;
* [ ] логировать Reload;
* [ ] измерять время Reload.

### Решение по дальнейшему развитию

После JSON POC:

```text
JSON работает
→ автоматический Reload больше не нужен
→ Reload остаётся fallback/user action
```

Если JSON POC не покрывает весь необходимый сценарий:

```text
дорабатывается Reload fallback
```

Статус: временный/fallback.

# Будущий этап — Journal Service + SQLite 🔵

Переход выполняется только при подтверждённой необходимости.

Целевая архитектура:

```text
Revit
  │
  │ HTTP
  ▼
BIMTools Journal Service
  │
  ▼
SQLite
```

SQLite-файл:

```text
локальный диск сервера
```

не:

```text
R:\...\Journal.db
```

и не:

```text
\\server\share\Journal.db
```

### Условия перехода

Переход оправдан, если:

* [ ] JSON-файлов становится слишком много;
* [ ] нужен сложный поиск;
* [ ] нужен поиск по элементам;
* [ ] нужна аналитика;
* [ ] требуется централизованный API;
* [ ] производительность файлового журнала начинает ухудшаться;
* [ ] обслуживание файлового журнала становится сложнее,
  чем небольшой SQLite-сервис.

### План миграции

```text
JsonJournalWriter
      │
      │ тот же JournalEvent
      ▼
HttpJournalWriter
      │
      ▼
Journal Service
      │
      ▼
SQLite
```

При этом:

```text
NotificationService
ChangeRecord
JournalEvent
Elements[]
UX
```

не должны быть переписаны.

Статус: архитектурный резерв.
