# ADR

## ADR-001

### Отказ от внешней БД в пользу хранения данных в Revit-модели

### Решение

Не использовать внешнюю базу данных для хранения журнала изменений.

Данные журнала хранятся непосредственно внутри Revit-моделей
с использованием Extensible Storage.

Проверка новых записей выполняется при открытии,
синхронизации или обновлении связанных моделей.

### Причина

Такой подход позволяет:

* избежать развертывания отдельного сервера БД;
* не зависеть от SQL Server или другой СУБД;
* хранить данные непосредственно вместе с моделью;
* упростить установку и сопровождение BIM Tools.

### Статус

✔ Принято и реализовано.

## ADR-002

### Разделение сущностей изменения, адресата и статуса доставки

### Решение

Разделить данные на отдельные сущности:

**Изменение (Change)** — само сообщение:

* автор;
* комментарий;
* список элементов;
* дата;
* приоритет.

**Адресат (Recipient)** — отдельная запись для каждой целевой модели
(например, ОВ, ВК, КР).

**Статус доставки (DeliveryStatus)** — состояние для каждого адресата:

* отправлено;
* доставлено;
* прочитано;
* выполнено;
* отменено.

### Причина

Такой подход позволяет избежать ситуации, когда одно изменение имеет
только один общий статус, хотя разные разделы находятся на разных
этапах работы.

### Статус

✔ Принято и реализовано.

## ADR-003

### Проверка уведомлений через события Revit

### Решение

Использовать события Revit для автоматической проверки новых уведомлений.

Используемые события:

* `DocumentOpened`;
* `DocumentSynchronizedWithCentral`;
* `DocumentReloadedLatest`.

### Причина

Пользователь получает проверку новых изменений:

* при открытии проекта;
* после синхронизации;
* после обновления модели через Reload Latest.

### Статус

✔ Проверено экспериментально и реализовано.

## ADR-004

### Хранение журнала изменений в исходной модели

### Решение

Каждая запись изменения хранится в Extensible Storage той модели,
в которой изменение было создано.

Связанные модели не получают копию журнала.

При проверке уведомлений выполняется чтение журналов связанных моделей.

### Причина

Такой подход позволяет:

* избежать дублирования записей;
* сохранить единый источник изменения;
* не создавать конфликтов при синхронизации нескольких моделей.

### Последствия

Для получения уведомлений необходимо наличие связи между моделями.

Проверка выполняется через загруженные Revit Links.

### Статус

✔ Проверено экспериментально и реализовано.

## ADR-005

### Хранение статуса прочтения отдельно от журнала

### Решение

Информация о прочитанных уведомлениях хранится отдельно
от журнала изменений.

Используется Extensible Storage текущей модели
для хранения списка идентификаторов просмотренных записей.

### Причина

Статус прочтения является персональным состоянием пользователя
в конкретной модели и не должен изменять исходную запись изменения.

### Последствия

Один пользователь может прочитать уведомление,
а другой продолжит видеть его как новое.

### Статус

✔ Проверено экспериментально и реализовано.

## ADR-006

### Работа со связанными моделями только через чтение

### Решение

Связанные документы используются только для чтения журнала.

Изменение данных в связанных моделях автоматически не выполняется.

### Причина

Revit API ограничивает работу с документами,
полученными через `RevitLinkInstance`.

Кроме того, автоматическая запись в связанные модели
может привести к конфликтам синхронизации.

### Статус

✔ Принято и реализовано.

## ADR-007

### Автоматическое обновление через отдельный Updater

### Решение

Обновление BIM Tools выполняется автоматически через отдельное
приложение `BIMToolsUpdater.exe`.

Основная DLL плагина отвечает за:

* получение текущей версии;
* получение списка GitHub Releases;
* выбор подходящего стабильного релиза;
* сравнение версий;
* загрузку ZIP-пакета;
* проверку пакета через `UpdateInfo.json`;
* запуск Updater.

`BIMToolsUpdater.exe` отвечает за:

* ожидание завершения Revit;
* распаковку ZIP;
* определение файлов для обновления;
* создание резервных копий существующих файлов;
* замену нескольких файлов плагина;
* удаление backup после успешного обновления;
* восстановление предыдущей версии при ошибке;
* удаление новых файлов при rollback;
* удаление использованного ZIP после успешного обновления;
* отображение результата обновления;
* защиту от одновременного запуска через `Mutex`.

### Причина

Загруженная Revit DLL не должна самостоятельно заменять собственные
файлы во время работы Revit.

Отдельный процесс позволяет выполнить замену после завершения Revit
без ручного вмешательства пользователя.

### Последствия

* обновление выполняется автоматически;
* пользователь не должен вручную заменять DLL;
* проверка версии и загрузка пакета выполняются в фоне;
* фактическая замена файлов выполняется после закрытия Revit;
* при ошибке выполняется rollback;
* обновление может затрагивать несколько DLL и ресурсов одновременно;
* корректный уже загруженный пакет повторно не скачивается;
* обновление той же версии повторно не запускается;
* после успешного обновления временный ZIP удаляется;
* `BIMToolsUpdater.exe` не включается в обычный ZIP обновления;
* обновление самого Updater через механизм автообновления пока
  не выполняется и будет спроектировано после Sprint 5.

### Формат production-пакета

```text
BIMToolsUpdate_<version>.zip
├── RevitCopyParams.dll
├── Newtonsoft.Json.dll
├── UpdateInfo.json
└── Resources/*
```

### Проверка

Проверен полный цикл:

```text
GitHub Release
→ проверка версии
→ загрузка ZIP
→ проверка UpdateInfo.json
→ проверка версии пакета
→ запуск Updater
→ ожидание закрытия Revit
→ распаковка ZIP
→ создание backup
→ замена файлов
→ удаление backup
→ удаление ZIP
→ уведомление пользователя.
```

Проверены:

* обновление нескольких файлов;
* `RevitCopyParams.dll`;
* `Newtonsoft.Json.dll`;
* `UpdateInfo.json`;
* `Resources`;
* rollback;
* восстановление предыдущих файлов;
* удаление новых файлов при rollback;
* защита Updater через `Mutex`;
* повторный вызов загрузки существующего корректного пакета;
* отсутствие повторного обновления после установки той же версии.

Фактически проверен end-to-end сценарий:

```text
0.4.9 → 0.4.10
```

После обновления подтверждено:

```text
CurrentVersion: 0.4.10.0
LatestVersion: 0.4.10
UpdateAvailable: False
```

Также подтверждено:

* `BIMToolsUpdater` после завершения не остаётся запущенным;
* `.backup` отсутствуют;
* использованный ZIP удалён;
* установленная DLL имеет версию `0.4.10.0`.

### Статус

✔ Реализовано и экспериментально проверено на Revit 2023.

Основная механика автоматического обновления готова.

## ADR-008

### Установка плагина в пользовательский каталог

### Решение

Плагин размещается в пользовательском каталоге:

```text
%AppData%\Autodesk\Revit\Addins\2023\RevitCopyParams
```

Файл `.addin` размещается непосредственно в:

```text
%AppData%\Autodesk\Revit\Addins\2023\RevitCopyParams.addin
```

### Причина

Установка через `ProgramData` требует административных прав
для изменения файлов.

Автоматическое обновление через Updater не должно приводить
к появлению UAC-запроса при каждом обновлении.

### Миграция

Inno Setup удаляет возможную старую установку из:

```text
%ProgramData%\Autodesk\Revit\Addins\2023\RevitCopyParams
```

и старый `.addin`, после чего создаёт новую пользовательскую установку
в `%AppData%`.

### Текущая политика установщика

Установщик использует:

```ini
PrivilegesRequired=admin
```

Это осознанное решение.

Причины:

* возможная миграция старой установки из `ProgramData`;
* установка сертификата в машинные хранилища;
* необходимость выполнения административных операций
  первоначальным установщиком.

При обычном запуске пользователем, имеющим права администратора,
Windows может запрашивать только подтверждение UAC без ввода
других credentials.

При сценарии запуска обычным пользователем с вводом credentials
другого администратора отдельно не тестировалось.

При этом само автоматическое обновление установленного в `%AppData%`
плагина административных прав не требует.

### Статус

✔ Реализовано и проверено для Revit 2023.

Проверено:

* чистая установка;
* установка в `%AppData%`;
* миграция `ProgramData → AppData`;
* запуск плагина из пользовательского каталога;
* автоматическое обновление без UAC;
* корректная работа от текущего пользовательского профиля.

## ADR-009

### GitHub Releases как источник обновлений

### Решение

GitHub Releases репозитория BIM Tools используется как источник
информации о доступных версиях и пакетов обновления.

Плагин получает список Releases через GitHub API.

Для выбора релиза используются поля GitHub Release:

* `draft`;
* `prerelease`;
* `tag_name`.

Стабильным считается Release, у которого:

```text
draft = false
prerelease = false
```

Среди подходящих стабильных Releases выбирается самая высокая версия.

После выбора релиза фактическая версия ZIP дополнительно проверяется
через `UpdateInfo.json`, находящийся внутри пакета.

### Причина

Использование статусов самого GitHub Release надёжнее, чем попытка
определять стабильность только по имени тега или имени ZIP-файла.

### Production-соглашение

Стабильный production Release:

* публикуется как обычный GitHub Release;
* имеет `draft = false`;
* имеет `prerelease = false`;
* использует тег вида `vX.Y.Z`;
* содержит пакет `BIMToolsUpdate_X.Y.Z.zip`;
* внутри пакета `UpdateInfo.json` содержит ту же версию.

### Последствия

* для проверки обновлений требуется сетевой доступ;
* при недоступности GitHub плагин продолжает работать;
* отсутствие соединения не должно блокировать запуск Revit;
* draft Releases не используются;
* pre-release Releases не используются;
* выбирается максимальная стабильная версия;
* имя ZIP не является источником истины для версии пакета;
* `UpdateInfo.json` является дополнительной проверкой фактического пакета.

### Проверено экспериментально

Проверены сценарии:

* stable Release выбирается;
* `prerelease = true` исключается;
* draft Release исключается;
* суффикс в `tag_name` сам по себе не определяет стабильность;
* выбирается максимальная стабильная версия;
* Release с ZIP другой версии не проходит проверку пакета;
* корректный ZIP принимается;
* после установки новой версии повторное обновление не запускается.

### Статус

✔ Реализовано, проверено и формально закреплено.

## ADR-010

### Хранение сервисных данных BIM Tools в `%APPDATA%`

### Решение

Сервисные данные плагина и Updater хранятся отдельно от каталога
установленных файлов.

Используется каталог:

```text
%AppData%\BIMTools\RevitCopyParams
```

Структура:

```text
BIMTools
└── RevitCopyParams
    ├── Logs
    ├── Updates
    └── Temp
```

### Назначение каталогов

`Logs`:

* `UpdateStartup.log`;
* `Updater.log`.

`Updates`:

* временно загруженные ZIP-пакеты обновлений.

`Temp`:

* распакованные файлы текущего пакета;
* временные данные процесса обновления.

### Причина

Сервисные данные не должны смешиваться с установленными файлами
плагина и не должны требовать административных прав.

### Последствия

* логи доступны текущему пользователю;
* Updater может работать без доступа к `ProgramData`;
* после успешного обновления ZIP и backup удаляются;
* временная папка очищается и пересоздаётся при обновлении;
* каталог сервисных данных создаётся автоматически.

### Статус

✔ Реализовано и проверено.

## ADR-011

### Кодовая подпись исполняемых файлов и установщика

### Решение

Основные исполняемые компоненты BIM Tools подписываются сертификатом
`BIM Tools Development`.

Сертификат:

```text
CN=BIM Tools Development
2EDD86A85E525CE115896D4026DEDAC395E8766A
```

Подписываются:

* `RevitCopyParams.dll`;
* `BIMToolsUpdater.exe`;
* `BIMToolsSetup_<version>.exe`;
* `unins000.exe`.

Используются:

* SHA-256;
* RFC3161 timestamp;
* `signtool.exe`;
* timestamp service DigiCert.

### Автоматизация

Подпись DLL и Updater выполняется в Release Post-Build проекта
`RevitCopyParams`.

Порядок:

```text
BIMToolsUpdater build
→ RevitCopyParams build
→ sign DLL
→ verify DLL
→ verify existence of Updater
→ sign Updater
→ verify Updater
→ copy files
→ build UpdatePackage
→ create ZIP
```

Подпись установщика выполняется Inno Setup через зарегистрированный
Sign Tool:

```text
BIMToolsSign
```

Inno Setup автоматически подписывает:

* основной Setup EXE;
* Uninstaller.

Ошибки подписи или проверки считаются ошибками сборки.

### Сертификат

Файл:

```text
Installer\Certificate\BIMToolsDevelopment.cer
```

включается в установщик.

Во время установки сертификат импортируется в:

```text
LocalMachine\Root
LocalMachine\TrustedPublisher
```

### Причина

Единая подпись всех исполняемых компонентов позволяет:

* идентифицировать издателя;
* сохранять одинаковую цепочку доверия для DLL, Updater и Installer;
* избежать ситуации, когда обновление содержит неподписанный Updater;
* проверять целостность и происхождение Release-артефактов.

### Ограничения

Используемый сертификат является внутренним self-signed сертификатом.

Он предназначен для внутреннего доверия и не создаёт публичную
репутацию SmartScreen.

Для целевой машины сертификат должен быть установлен в доверенные
хранилища Windows.

### Проверено экспериментально

Проверено:

* ручная подпись DLL;
* автоматическая подпись DLL в Post-Build;
* ручная подпись Updater;
* автоматическая подпись Updater в Post-Build;
* автоматическая подпись Installer через Inno Setup;
* автоматическая подпись Uninstaller;
* `signtool verify /pa /v`;
* `Get-AuthenticodeSignature`.

Для проверенных файлов получен:

```text
Status = Valid
Thumbprint = 2EDD86A85E525CE115896D4026DEDAC395E8766A
```

На тестовой машине после установки сертификат присутствует в:

```text
LocalMachine\Root
LocalMachine\TrustedPublisher
```

Также проверена подпись файлов после установки и после
автоматического обновления.

### Статус

✔ Реализовано и экспериментально проверено.

## ADR-012

### Production-процесс сборки, подписи и публикации Release

### Решение

Процесс создания production-версии BIM Tools выполняется
последовательно и состоит из двух независимых стадий:

**1. Release Build**

```text
BIMToolsUpdater
→ RevitCopyParams
→ Post-Build
```

Post-Build основного проекта:

* подписывает `RevitCopyParams.dll`;
* проверяет подпись DLL;
* проверяет наличие `BIMToolsUpdater.exe`;
* подписывает `BIMToolsUpdater.exe`;
* проверяет подпись Updater;
* копирует подписанные файлы в локальную установку;
* формирует `UpdatePackage`;
* создаёт `UpdateInfo.json`;
* создаёт `BIMToolsUpdate_<version>.zip`.

**2. Installer Build**

Inno Setup:

* берёт свежую Release DLL;
* берёт подписанный Updater;
* включает сертификат `.cer`;
* формирует Installer;
* подписывает Setup;
* подписывает Uninstaller.

### Production-чеклист

Перед публикацией:

1. выполнить `Rebuild Solution` в `Release`;
2. убедиться, что DLL и Updater подписаны и проверены;
3. убедиться, что создан ZIP соответствующей версии;
4. собрать Inno Setup;
5. убедиться, что Setup и Uninstaller подписаны;
6. проверить Setup через `signtool verify`;
7. выполнить установку/обновление на тестовой машине;
8. проверить запуск Revit;
9. проверить автообновление;
10. проверить отсутствие повторного обновления той же версии;
11. только после этого публиковать production Release.

### Production-артефакты

В production используются:

```text
BIMToolsUpdate_<version>.zip
BIMToolsSetup_<version>.exe
```

GitHub Release должен соответствовать той же версии.

### Причина

Последовательный процесс позволяет исключить публикацию:

* неподписанной DLL;
* неподписанного Updater;
* неподписанного Installer;
* ZIP с несовпадающей версией;
* Installer, собранного до завершения Release Build.

### Статус

✔ Процесс реализован и практически проверен.

Первичный production-сценарий успешно пройден на версиях:

```text
0.4.9 → 0.4.10
```

Первым stable installer считается проверенный:

```text
BIMToolsSetup_0.4.9.0.exe
```
