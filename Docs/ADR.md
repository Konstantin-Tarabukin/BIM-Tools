# ADR

## ADR-001

### Отказ от внешней БД в пользу хранения данных в Revit-модели

### Решение

Не использовать внешнюю базу данных для хранения журнала изменений.

Данные журнала хранятся непосредственно внутри Revit-моделей
с использованием Extensible Storage.

Проверка новых записей выполняется при открытии, синхронизации
или обновлении связанных моделей.

### Причина

Такой подход позволяет:

* избежать развертывания отдельного сервера БД;
* не зависеть от SQL Server или другой СУБД;
* хранить данные непосредственно вместе с моделью;
* упростить установку и сопровождение BIM Tools.

### Статус

✔ Принято и реализовано.

## ADR-002

### Разделение сущностей изменения, адресата и статуса доставки

### Решение

Разделить данные на отдельные сущности:

**Изменение (Change)** — само сообщение:

* автор;
* комментарий;
* список элементов;
* дата;
* приоритет.

**Адресат (Recipient)** — отдельная запись для каждой целевой модели
(например, ОВ, ВК, КР).

**Статус доставки (DeliveryStatus)** — состояние для каждого адресата:

* отправлено;
* доставлено;
* прочитано;
* выполнено;
* отменено.

### Причина

Такой подход позволяет избежать ситуации, когда одно изменение имеет
только один общий статус, хотя разные разделы находятся на разных
этапах работы.

### Статус

✔ Принято и реализовано.

## ADR-003

### Проверка уведомлений через события Revit

### Решение

Использовать события Revit для автоматической проверки новых уведомлений.

Используемые события:

* `DocumentOpened`;
* `DocumentSynchronizedWithCentral`;
* `DocumentReloadedLatest`.

### Причина

Пользователь гарантированно получает проверку новых изменений:

* при открытии проекта;
* после синхронизации;
* после обновления модели через Reload Latest.

### Статус

✔ Проверено экспериментально и реализовано.

## ADR-004

### Хранение журнала изменений в исходной модели

### Решение

Каждая запись изменения хранится в Extensible Storage той модели,
в которой изменение было создано.

Связанные модели не получают копию журнала.

При проверке уведомлений выполняется чтение журналов связанных моделей.

### Причина

Такой подход позволяет:

* избежать дублирования записей;
* сохранить единый источник изменения;
* не создавать конфликтов при синхронизации нескольких моделей.

### Последствия

Для получения уведомлений необходимо наличие связи между моделями.

Проверка выполняется через загруженные Revit Links.

### Статус

✔ Проверено экспериментально и реализовано.

## ADR-005

### Хранение статуса прочтения отдельно от журнала

### Решение

Информация о прочитанных уведомлениях хранится отдельно
от журнала изменений.

Используется Extensible Storage текущей модели
для хранения списка идентификаторов просмотренных записей.

### Причина

Статус прочтения является персональным состоянием пользователя
в конкретной модели и не должен изменять исходную запись изменения.

### Последствия

Один пользователь может прочитать уведомление,
а другой продолжит видеть его как новое.

### Статус

✔ Проверено экспериментально и реализовано.

## ADR-006

### Работа со связанными моделями только через чтение

### Решение

Связанные документы используются только для чтения журнала.

Изменение данных в связанных моделях автоматически не выполняется.

### Причина

Revit API ограничивает работу с документами,
полученными через `RevitLinkInstance`.

Кроме того, автоматическая запись в связанные модели
может привести к конфликтам синхронизации.

### Статус

✔ Принято и реализовано.

## ADR-007

### Автоматическое обновление через отдельный Updater

### Решение

Обновление BIM Tools выполняется автоматически через отдельное
приложение `BIMToolsUpdater.exe`.

Основная DLL плагина отвечает за:

* получение текущей версии;
* получение списка GitHub Releases;
* выбор подходящего стабильного релиза;
* сравнение версий;
* загрузку ZIP-пакета;
* проверку пакета через `UpdateInfo.json`;
* запуск Updater.

`BIMToolsUpdater.exe` отвечает за:

* ожидание завершения Revit;
* распаковку ZIP;
* определение файлов для обновления;
* создание резервных копий существующих файлов;
* замену нескольких файлов плагина;
* удаление backup после успешного обновления;
* восстановление предыдущей версии при ошибке;
* удаление новых файлов при rollback;
* удаление использованного ZIP после успешного обновления;
* отображение результата обновления.

### Причина

Загруженная Revit DLL не должна самостоятельно заменять собственные
файлы во время работы Revit.

Отдельный процесс позволяет выполнить замену после завершения Revit
без ручного вмешательства пользователя.

### Последствия

* обновление выполняется автоматически;
* пользователь не должен вручную заменять DLL;
* Revit продолжает работать во время проверки и загрузки;
* фактическая замена файлов выполняется после закрытия Revit;
* при ошибке выполняется rollback;
* обновление может затрагивать несколько DLL и ресурсов одновременно;
* повторное скачивание уже существующего корректного пакета не выполняется;
* для обновления используется отдельный исполняемый файл Updater;
* после успешного обновления временный ZIP удаляется.

### Проверка

Проверен полный цикл:

```text
GitHub Release
→ проверка версии
→ загрузка ZIP
→ проверка UpdateInfo.json
→ запуск Updater
→ ожидание закрытия Revit
→ распаковка ZIP
→ создание backup
→ замена файлов
→ удаление backup
→ удаление ZIP
→ уведомление пользователя.
```

Проверен сценарий ошибки:

```text
ошибка обновления
→ rollback
→ восстановление предыдущих файлов
→ удаление новых файлов.
```

Проверено обновление нескольких компонентов:

* `RevitCopyParams.dll`;
* `Newtonsoft.Json.dll`;
* `UpdateInfo.json`;
* папка `Resources`.

Проверено:

* SHA-256 установленного файла относительно файла из ZIP;
* защита Updater через `Mutex`;
* повторный вызов `DownloadUpdate()` с уже существующим корректным ZIP;
* отсутствие повторного обновления после установки той же версии.

### Статус

✔ Реализовано и экспериментально проверено на Revit 2023.

## ADR-008

### Установка плагина в пользовательский каталог

### Решение

Плагин размещается в пользовательском каталоге `%AppData%`,
доступном текущему пользователю без административных прав.

Используемый каталог:

`%AppData%\Autodesk\Revit\Addins\2023\RevitCopyParams`

Файл `.addin` также размещается в пользовательском каталоге.

### Причина

Установка через `ProgramData` требует административных прав
для изменения файлов.

Автоматическое обновление через Updater не должно приводить
к появлению UAC-запроса при каждом обновлении.

### Последствия

* автоматическое обновление не требует прав администратора;
* пользователь может обновлять плагин без UAC;
* первоначальный установщик должен учитывать миграцию старой установки;
* необходимо учитывать версии Revit.

### Статус

✔ Реализовано и проверено экспериментально.

Проверено:

* чистая установка;
* установка в `%AppData%`;
* отсутствие UAC при автоматическом обновлении;
* миграция `ProgramData → AppData`;
* запуск плагина из пользовательского каталога.

На текущем этапе Inno Setup всё ещё может требовать права администратора,
поскольку установщик удаляет возможную старую установку из
`ProgramData`.

Само автоматическое обновление установленного в `%AppData%`
плагина административных прав не требует.

## ADR-009

### GitHub Releases как источник обновлений

### Решение

GitHub Releases репозитория BIM Tools используется как источник
информации о доступных версиях и пакетов обновления.

Плагин получает список Releases через GitHub API.

Для выбора релиза используются поля GitHub Release:

* `draft`;
* `prerelease`;
* `tag_name`.

Стабильным считается Release, у которого:

```text
draft = false
prerelease = false
```

Суффиксы в `tag_name` (`-test`, `-beta`, `-alpha` и т. п.) сами по себе
не определяют стабильность релиза.

Среди подходящих стабильных Releases выбирается самая высокая версия.

После выбора релиза фактическая версия ZIP дополнительно проверяется
через `UpdateInfo.json`, находящийся внутри пакета.

### Причина

GitHub уже используется как репозиторий исходного кода проекта
и предоставляет Releases и загрузку файлов.

Использование статусов самого GitHub Release надёжнее, чем попытка
определять стабильность только по имени тега или имени ZIP-файла.

Дополнительная проверка `UpdateInfo.json` защищает от ситуации,
когда Release содержит ZIP пакета другой версии.

### Последствия

* для проверки обновлений требуется сетевой доступ;
* при недоступности GitHub плагин продолжает работать;
* отсутствие соединения не должно блокировать запуск Revit;
* draft Releases не используются;
* pre-release Releases не используются;
* выбирается максимальная стабильная версия;
* имя ZIP не является источником истины для версии пакета;
* версия `UpdateInfo.json` используется как окончательная проверка
  фактического пакета;
* требуется поддерживать понятное соглашение по production stable tags.

### Проверено экспериментально

Проверены сценарии:

* stable Release выбирается;
* `prerelease = true` исключается;
* draft Release исключается;
* `v0.4.4-test` с `prerelease = true` исключается;
* тот же тег при `prerelease = false` не исключается автоматически
  только из-за суффикса;
* выбирается максимальная стабильная версия;
* Release `0.4.4` с ZIP, содержащим `UpdateInfo.json` версии `0.4.3`,
  не проходит проверку пакета;
* корректный ZIP `0.4.4` принимается;
* после установки `0.4.4` повторное обновление не запускается.

### Статус

✔ Реализовано и экспериментально проверено.

Перед первым production release остаётся формально закрепить
соглашение по именованию стабильных тегов и выполнить несколько
последовательных production-обновлений.

## Текущее архитектурное состояние

Sprint 8 сформировал следующую архитектуру:

```text
RevitCopyParams.dll
        ↓
UpdateStartupService
        ↓
UpdateService
        ↓
GitHub Releases
        ↓
стабильный Release
        ↓
ZIP
        ↓
UpdateInfo.json
        ↓
проверка версии пакета
        ↓
BIMToolsUpdater.exe
        ↓
ожидание закрытия Revit
        ↓
backup
        ↓
замена файлов
        ↓
rollback при ошибке
        ↓
удаление backup и ZIP
        ↓
немодальное уведомление
```

Первоначальная установка выполняется через Inno Setup.

Последующие обновления выполняются через GitHub Release и
`BIMToolsUpdater.exe`.

### Итоговый статус

Основная архитектура автоматического обновления реализована,
проверена на Revit 2023 и готова к финальной production-проверке
и первому полноценному stable release.
