# ADR

## ADR-001

### Отказ от внешней БД в пользу хранения данных в Revit-модели

### Историческое решение

На первоначальном этапе BIM Tools не использовал внешнюю базу данных
для хранения журнала изменений.

Данные журнала хранились непосредственно внутри Revit-моделей
с использованием Extensible Storage.

Проверка новых записей выполнялась при открытии,
синхронизации или обновлении связанных моделей.

### Причина первоначального решения

Такой подход позволял:

* избежать развертывания отдельного сервера БД;
* не зависеть от SQL Server или другой СУБД;
* хранить данные непосредственно вместе с моделью;
* упростить установку и сопровождение BIM Tools.

### Текущее состояние

Extensible Storage остаётся частью текущей рабочей реализации
и используется как резервный механизм во время перехода
на внешний журнал.

Для новой архитектуры внешнего журнала настоящее решение
считается **заменённым ADR-014**.

### Статус

🟡 Историческое решение / superseded by ADR-014.

## ADR-002

### Разделение сущностей изменения, адресата и статуса доставки

### Решение

Разделить данные на отдельные сущности:

**Изменение (Change)** — само сообщение:

* автор;
* комментарий;
* список элементов;
* дата;
* приоритет.

**Адресат (Recipient)** — отдельная запись для каждой целевой модели
(например, ОВ, ВК, КР).

**Статус доставки (DeliveryStatus)** — состояние для каждого адресата:

* отправлено;
* доставлено;
* прочитано;
* выполнено;
* отменено.

### Причина

Такой подход позволяет избежать ситуации, когда одно изменение имеет
только один общий статус, хотя разные разделы находятся на разных
этапах работы.

### Статус

✔ Принято и реализовано.

Для внешнего JSON-журнала структура сущностей сохраняется.

## ADR-003

### Проверка уведомлений через события Revit

### Решение

Использовать события Revit и фоновый polling внешнего журнала
для автоматической проверки новых уведомлений.

Текущая реализация использует:

* `DocumentOpened`;
* `DocumentSynchronizedWithCentral`;
* `DocumentReloadedLatest`.

После перехода на внешний журнал:

* `DocumentOpened` остаётся точкой первоначальной проверки;
* `DocumentSynchronizedWithCentral` используется для фиксации
  собственных изменений и запуска проверки внешнего журнала;
* `DocumentReloadedLatest` сохраняется для совместимости
  с текущим механизмом;
* основной источник новых уведомлений становится внешний Journal;
* получение уведомления больше не должно требовать Reload
  связанной модели.

Внешний журнал проверяется через polling.

Проверка должна читать только новые записи,
а не перечитывать всю историю проекта.

### Переходный период

На этапе POC одновременно существуют:

```text
Extensible Storage
+
External JSON Journal
```

Extensible Storage остаётся резервным/legacy-механизмом.

После успешной валидации JSON-пути уведомления переходят
на внешний журнал.

### Причина

Текущий механизм требует актуального `RevitLinkDocument`,
а его получение может приводить к Reload связанных моделей.

Reload:

* увеличивает время пользовательской операции;
* регенерирует host-документ;
* может очищать Undo history;
* зависит от ограничений Revit API.

Внешний журнал позволяет получить факт изменения
без загрузки изменённого RVT.

### Последствия

Пользователь может получить:

```text
модель изменена
→ notification
→ список изменённых элементов
→ возможность подсветки
```

без автоматического Reload.

Reload становится отдельной операцией,
которая выполняется только когда действительно требуется
актуальное содержимое модели.

### Статус

🟡 Основная текущая механика реализована.

🟡 Архитектура находится в переходе на ADR-014.

## ADR-004

### Хранение журнала изменений в исходной модели

### Историческое решение

Каждая запись изменения хранится в Extensible Storage той модели,
в которой изменение было создано.

Связанные модели не получают копию журнала.

При проверке уведомлений выполняется чтение журналов связанных моделей.

### Текущее состояние

Это правило сохраняется для Legacy Extensible Storage.

Для внешнего журнала источником записи становится
общий журнал проекта:

```text
<ProjectRoot>\_BIMToolsJournal\
```

При этом автором события по-прежнему считается модель,
в которой изменение создано.

### Причина

Сохранение `SourceModel` в событии позволяет не терять информацию
об источнике изменения при переходе от хранения внутри модели
к внешнему журналу.

### Последствия

Внешний журнал становится независимым от необходимости загрузки
исходной модели.

Связь между моделями продолжает использоваться Revit
для определения структуры проекта и доступа к элементам,
но больше не является обязательным каналом доставки самого
уведомления.

### Статус

✔ Реализовано для Extensible Storage.

🟡 Внешняя реализация будет выполнена в рамках ADR-014.

## ADR-005

### Хранение статуса прочтения отдельно от журнала

### Решение

Информация о прочитанных уведомлениях не хранится
в общей записи изменения.

Для текущей Extensible Storage-реализации используется
Extensible Storage текущей модели.

Для внешнего JSON-журнала состояние прочтения хранится
локально у пользователя:

```text
%AppData%\BIMTools\RevitCopyParams\JournalState.json
```

В состояние входят идентификаторы уже обработанных событий.

### Причина

Статус прочтения является персональным состоянием пользователя
и не должен изменять общий файл события.

При внешнем журнале это особенно важно:

один пользователь может считать событие прочитанным,
а другой должен продолжать видеть его как новое.

### Статус

✔ Реализовано для текущей архитектуры.

🟡 Механизм внешнего состояния будет дополнен в рамках ADR-014.

## ADR-006

### Работа со связанными моделями только через чтение

### Решение

Содержимое связанных моделей используется только для чтения.

Изменение данных непосредственно в связанных документах
автоматически не выполняется.

При необходимости обновления link BIM Tools изменяет состояние
самого host-документа, используя API `RevitLinkType.Reload()`.

Это не является записью в связанную модель:
Reload только повторно загружает связанный документ
в контекст текущего host-документа.

### Причина

Revit API ограничивает работу с документами,
полученными через `RevitLinkInstance`.

Кроме того, автоматическая запись в связанные модели
может привести к конфликтам синхронизации.

### Текущее состояние

Для новой архитектуры внешний журнал позволяет
не выполнять Reload для самой доставки уведомления.

Reload остаётся отдельным механизмом актуализации содержимого,
если пользователь действительно хочет получить свежую версию link.

### Статус

✔ Принято и реализовано.

## ADR-007

### Автоматическое обновление через отдельный Updater

### Решение

Обновление BIM Tools выполняется автоматически через отдельное
приложение `BIMToolsUpdater.exe`.

Основная DLL плагина отвечает за:

* получение текущей версии;
* получение списка GitHub Releases;
* выбор подходящего стабильного релиза;
* сравнение версий;
* загрузку ZIP-пакета;
* проверку пакета через `UpdateInfo.json`;
* запуск Updater.

`BIMToolsUpdater.exe` отвечает за:

* ожидание завершения Revit;
* распаковку ZIP;
* определение файлов для обновления;
* создание резервных копий существующих файлов;
* замену нескольких файлов плагина;
* удаление backup после успешного обновления;
* восстановление предыдущей версии при ошибке;
* удаление новых файлов при rollback;
* удаление использованного ZIP после успешного обновления;
* отображение результата обновления;
* защиту от одновременного запуска через `Mutex`.

### Причина

Загруженная Revit DLL не должна самостоятельно заменять собственные
файлы во время работы Revit.

### Статус

✔ Реализовано и экспериментально проверено на Revit 2023.

## ADR-008

### Установка плагина в пользовательский каталог

### Решение

Плагин размещается в пользовательском каталоге:

```text
%AppData%\Autodesk\Revit\Addins\2023\RevitCopyParams
```

Файл `.addin` размещается непосредственно в:

```text
%AppData%\Autodesk\Revit\Addins\2023\RevitCopyParams.addin
```

### Причина

Установка через `ProgramData` требует административных прав
для изменения файлов.

Автоматическое обновление через Updater не должно приводить
к появлению UAC-запроса при каждом обновлении.

### Статус

✔ Реализовано и проверено для Revit 2023.

---

## ADR-009

### GitHub Releases как источник обновлений

### Решение

GitHub Releases репозитория BIM Tools используется как источник
информации о доступных версиях и пакетов обновления.

Для выбора релиза используются поля:

* `draft`;
* `prerelease`;
* `tag_name`.

Стабильным считается Release, у которого:

```text
draft = false
prerelease = false
```

### Статус

✔ Реализовано, проверено и формально закреплено.

## ADR-010

### Хранение сервисных данных BIM Tools в `%APPDATA%`

### Решение

Сервисные данные плагина и Updater хранятся отдельно
от каталога установленных файлов.

Используется:

```text
%AppData%\BIMTools\RevitCopyParams
```

Структура:

```text
BIMTools
└── RevitCopyParams
    ├── Logs
    ├── Updates
    └── Temp
```

### Статус

✔ Реализовано и проверено.

Для внешнего журнала этот каталог также используется
для локального состояния клиента.

## ADR-013

### Актуализация Revit Links после синхронизации

### Контекст

В ходе production-like тестирования обнаружено,
что после успешного Sync host-модель может продолжать работать
со старым состоянием `RevitLinkDocument`.

Из-за этого новая запись Extensible Storage становится доступной
только после Reload link.

### Историческое решение

После успешного:

```text
DocumentSynchronizedWithCentral
```

перед проверкой уведомлений выполнять Reload доступных
loaded top-level Revit Links.

### Текущее архитектурное состояние

Это решение остаётся допустимым **для текущего Extensible Storage
механизма**, но больше не является целевой архитектурой доставки
уведомлений.

После внедрения ADR-014 внешний журнал позволяет получать:

```text
Sync
→ JSON event
→ notification
```

без Reload.

Поэтому разработка сложной оптимизации `RevitLinkReloadService`
не должна блокировать переход на внешний журнал.

Существующая Reload-логика может быть сохранена как:

* fallback;
* legacy notification path;
* механизм принудительной актуализации link
  при явном запросе пользователя.

### Статус

🟡 Принято как переходный/fallback-механизм.

⏸ Оптимизация и расширение не должны блокировать JSON POC.

# ADR-014

## Внешний журнал изменений на основе JSON с заменяемым backend

### Контекст

Текущий механизм уведомлений хранит журнал изменений
в Extensible Storage внутри RVT-моделей.

Для получения новых записей из связанных моделей
необходимо актуальное состояние `RevitLinkDocument`.

На практике это может приводить к:

```text
Synchronize
→ Reload links
→ чтение журнала
→ notification
```

При наличии нескольких связей Reload заметно увеличивает
время пользовательского Sync.

Дополнительно требуется будущая возможность хранить
привязанные к изменению элементы модели и показывать их
получателю без предварительного Reload.

Необходим механизм, который:

* не требует отдельной БД для первого этапа;
* не требует нового сервера;
* может использовать существующее сетевое хранилище проектов;
* не создаёт единого файла, который одновременно изменяется
  несколькими клиентами;
* позволяет хранить историю событий;
* поддерживает список изменённых элементов;
* позволяет позднее перейти на SQLite без переписывания
  бизнес-логики журнала.

### Решение

Ввести внешний журнал изменений на основе отдельных JSON-файлов.

Для первого POC журнал размещается внутри существующей
сетевой структуры проекта.

Пример:

```text
R:\05091-ЭФ25\
├── AR\
├── KR\
├── VK\
├── OV\
└── _BIMToolsJournal\
```

Структура внешнего журнала:

```text
_BIMToolsJournal\
└── Events\
    └── 2026\
        └── 09\
            └── 08\
                ├── AR\
                ├── KR\
                ├── VK\
                └── OV\
```

Для другого проекта используется его собственный журнал:

```text
R:\06021-...\_BIMToolsJournal\
```

Таким образом журнал естественным образом изолирован
на уровне проекта.

### Формат события

Каждое изменение хранится в отдельном JSON-файле.

Файл содержит концептуально:

```text
SchemaVersion
EventId
ProjectId
ModelId
ModelName
Author
CreatedUtc
EventType
Message
Elements[]
```

Пример:

```json
{
  "schemaVersion": 1,
  "eventId": "7f3a2b42-2d52-4b72-9af2-123456789abc",
  "projectId": "05091-ЭФ25",
  "modelId": "AR",
  "modelName": "05091-ЭФ25_АР",
  "author": "User1",
  "createdUtc": "2026-09-08T14:05:01.123Z",
  "eventType": "ElementsChanged",
  "message": "Изменены элементы",
  "elements": [
    {
      "uniqueId": "....",
      "elementId": 123456,
      "category": "Walls",
      "name": "..."
    }
  ]
}
```

### Уникальность события

Каждый event получает новый GUID:

```text
EventId = Guid.NewGuid()
```

`EventId` является уникальным идентификатором события.

Не используется:

```text
MAX(Id) + 1
```

или другой общий клиентский счётчик.

### Один event — один файл

Не использовать единый большой JSON-файл.

Каждое отдельное изменение сохраняется как отдельный файл:

```text
event-<GUID>.json
```

Если одно пользовательское действие затронуло
несколько элементов, создаётся:

```text
1 event
+
Elements[]
```

а не отдельный JSON для каждого элемента.

### Организация файлов

Файлы распределяются по:

```text
Project
→ Year
→ Month
→ Day
→ Model
```

Например:

```text
05091-ЭФ25\_BIMToolsJournal\Events\2026\09\08\AR\
```

Это позволяет не сканировать многолетнюю историю журнала
при обычной работе клиента.

### Чтение журнала

Не разрешается выполнять:

```text
Directory.GetFiles(
    journalRoot,
    "*.json",
    SearchOption.AllDirectories)
```

на каждом цикле проверки.

Клиент:

1. определяет текущий проект;
2. определяет актуальный период;
3. использует локальное состояние последнего обработанного события;
4. читает только необходимые каталоги;
5. обрабатывает только новые `EventId`.

### Polling

Для первого POC используется polling.

Не использовать `FileSystemWatcher` как обязательную часть
архитектуры.

Причина:

* сетевые файловые системы имеют особенности доставки
  событий файловой системы;
* polling проще контролировать;
* polling позволяет явно ограничить объём читаемых данных;
* частота polling может быть настроена отдельно
  от пользовательских Revit-событий.

### Атомарная запись

Файл не создаётся сразу как готовый `.json`.

Используется схема:

```text
event.tmp
→ полностью записать
→ закрыть файл
→ переименовать
→ event.json
```

Клиент читает только:

```text
*.json
```

Файлы:

```text
*.tmp
```

считаются незавершёнными.

### Хранилище пути

В коде не должен быть жёстко зашит:

```text
R:
```

Используется конфигурируемый UNC-путь.

Например:

```text
\\server\share\05091-ЭФ25\_BIMToolsJournal
```

или путь к соответствующей папке проекта.

Буква диска `R:` рассматривается только как пользовательское
отображение сетевого ресурса.

### Локальное состояние клиента

Каждый Revit-клиент хранит состояние обработки отдельно:

```text
%AppData%\BIMTools\RevitCopyParams\JournalState.json
```

В состоянии хранятся:

* последний обработанный период;
* обработанные `EventId`;
* при необходимости дополнительные метаданные
  для восстановления после сбоя.

Общее состояние прочтения в сетевой папке не создаётся.

### Поведение при недоступности сетевого журнала

Недоступность внешнего журнала:

```text
не должна блокировать Sync;
не должна вызывать падение плагина;
не должна отменять пользовательскую операцию;
```

Ошибка должна:

```text
→ записываться в локальный лог
→ обработка продолжаться
→ запись попытаться отправить повторно
```

Extensible Storage в переходном режиме сохраняет
резервную доставку.

### Dual Write

На этапе POC запись выполняется одновременно:

```text
ChangeRecord
    │
    ├──> Extensible Storage
    │
    └──> External JSON Journal
```

Это необходимо для безопасного сравнения старой и новой
архитектуры.

После успешного POC внешний журнал становится новым
источником уведомлений, а Extensible Storage некоторое время
может сохраняться как fallback.

### Отделение модели данных от backend

Бизнес-сущность события не должна зависеть от конкретного способа
хранения.

Ввести логический интерфейс:

```text
IJournalWriter
IJournalReader
```

или эквивалентный абстрактный storage API.

На первом этапе:

```text
JsonJournalWriter
JsonJournalReader
```

В дальнейшем возможна реализация:

```text
HttpJournalWriter
HttpJournalReader
        ↓
BIMTools Journal Service
        ↓
SQLite
```

При этом `ChangeRecord`, `JournalEvent`,
логика уведомлений и привязка элементов
не должны зависеть от SQLite.

### Почему SQLite не используется сейчас

Не использовать SQLite напрямую на сетевой папке:

```text
R:\...\BIMToolsJournal.db
```

с несколькими Revit-клиентами.

Причина:

* единый файл БД становится общей точкой записи;
* сетевой файловый доступ увеличивает сложность блокировок;
* схема плохо отделяет клиентскую логику от хранения;
* такой вариант не даёт преимуществ полноценного
  серверного DB-сервиса.

Если SQLite понадобится, использовать:

```text
Revit
→ Journal Service
→ local SQLite
```

где SQLite-файл находится локально на машине,
на которой работает Journal Service.

### Когда переходить на SQLite

Переход на:

```text
Journal Service + SQLite
```

рассматривается, если появляются:

* большое количество событий;
* необходимость сложного поиска;
* запросы по `ElementId` / `UniqueId`;
* аналитика;
* длительное хранение больших объёмов;
* сложные индексы;
* централизованное управление доступом;
* необходимость API вместо прямого SMB;
* проблемы обслуживания большого количества файлов.

### Привязка элементов

Внешний event поддерживает список:

```text
Elements[]
```

Основным стабильным идентификатором элемента используется:

```text
Element.UniqueId
```

`ElementId` хранится как дополнительная информация.

Дополнительно могут сохраняться:

* категория;
* имя;
* тип;
* модель-источник.

Это позволяет использовать журнал для будущего UX:

```text
Notification
→ Показать изменения
→ найти элементы
→ подсветить элементы
```

без необходимости сначала Reload исходной RVT-модели.

### Разделение уведомления и Reload

После внедрения внешнего журнала:

```text
Sync
→ Journal Event
→ Notification
```

не должен автоматически приводить к:

```text
Reload Link
```

Пользователь получает информацию об изменении отдельно
от актуализации полного содержимого модели.

Reload выполняется:

* при явном запросе пользователя;
* в сценариях, где реально необходимо свежее содержимое link;
* временно — для legacy Extensible Storage-механизма.

### Производительность

Главная цель POC:

```text
Sync
→ создать JSON
→ другой Revit получает notification
```

без:

```text
Reload
```

и без ощутимой задержки пользовательского Sync.

Проверка журнала не должна перечитывать всю историю.

Рост общей истории:

```text
10 000
100 000
500 000
```

не должен линейно увеличивать время обычного polling,
поскольку журнал разделён по проекту, дате и модели.

### Архивирование

Исторические данные должны иметь возможность
периодического архивирования.

Базовая схема:

```text
Events\
Archive\
```

На первом этапе архивирование не блокирует POC.

### Безопасность

Внешний журнал использует уже существующие права
на сетевую папку проекта.

Не создаётся отдельная SQL-учётная запись.

Права должны позволять:

* создание событий пользователями BIM Tools;
* чтение событий пользователями BIM Tools;
* отсутствие необходимости прямого доступа
  к SQLite-файлу в будущем.

### Совместимость

Каждый event содержит:

```text
SchemaVersion
```

Изменение схемы JSON выполняется через версионирование,
а не через неявное изменение значения существующих полей.

Старые записи должны оставаться читаемыми.

### Миграция

На первом этапе миграция старого Extensible Storage журнала
в JSON не является обязательной.

Новые записи:

```text
ES + JSON
```

Старые записи:

```text
ES
```

После стабилизации системы может быть реализован
отдельный импорт исторического журнала.

### Последствия

Плюсы:

* не требуется отдельный сервер;
* не требуется SQLite для POC;
* используется существующее сетевое хранилище;
* очень простой deployment;
* события легко диагностировать;
* один event не блокирует другие;
* история не влияет напрямую на обычный polling;
* можно хранить элементы;
* можно отказаться от Reload для доставки уведомлений;
* backend можно позднее заменить на SQLite Service.

Минусы:

* большое количество маленьких файлов;
* сложные исторические запросы менее эффективны,
  чем SQL;
* необходимо правильно реализовать индексацию через структуру каталогов
  и локальное состояние;
* надёжность зависит от доступности сетевого хранилища;
* при очень большом объёме потребуется архивирование или миграция
  на SQLite.

### Статус

🟡 Принято к реализации.

Первый этап:

```text
JSON Journal POC
```

Целевая стратегия:

```text
JSON backend
→ доказательство концепции
→ при необходимости
Journal Service + SQLite
```

# ADR-015

### Отложенный переход от JSON к SQLite через Journal Service

### Решение

Если JSON-журнал перестанет обеспечивать необходимый уровень
производительности, поиска или сопровождения, замена backend
выполняется через отдельный Journal Service.

Целевая схема:

```text
Revit Client
      │
      │ HTTP
      ▼
BIMTools Journal Service
      │
      ▼
local SQLite
```

SQLite не размещается непосредственно на сетевой SMB-шаре
и не открывается несколькими Revit-клиентами напрямую.

### Причина

Такой переход позволяет сохранить:

* существующую модель `JournalEvent`;
* идентификатор `EventId`;
* `ProjectId`;
* `ModelId`;
* `Elements[]`;
* notification logic;
* UX;
* локальное состояние пользователя.

Меняется только backend.

### Статус

🔵 Запланировано.

Переход выполняется только после появления подтверждённой
необходимости.
